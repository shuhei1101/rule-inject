# セットアップ

プラグインを読み込み、スキルで端末とリポジトリをセットアップするまでの手順

## 前提条件

| 項目 | 内容 |
| --- | --- |
| OS | Linux か WSL（macOS と、WSL を使わない Windows は対象外） |
| `python3` | 3.12 以上。フックが端末の `python3` で動く |

> [!WARNING]
> `python3` が 3.12 より古いと、フックは動かず、「フックには Python 3.12 以上が要ること」と動いたバージョンがコンテキストに載る。

## 手順

### 1. プラグインを読み込む

Claude Code で、このリポジトリを marketplace として追加し、プラグインを入れる。

```text
/plugin marketplace add shuhei1101/rule-inject
/plugin install rule-inject@rule-inject
```

一度入れれば、起動のたびに指定しなくてよい。
新しいバージョンは `/plugin marketplace update rule-inject` で取り込む。

プラグインはフック 7 つ（`PreToolUse`・`PostToolUse` 2 つ・`PreCompact`・`SessionStart` 3 つ）を持つ。

### 2. 端末をセットアップする

スキル `global-setup` を実行する。

```text
/rule-inject:global-setup
```

端末の設定の作成か移し替え、MCP サーバーの起動と接続の確認、フックの確認までを実行し、作ったものと結果を示す。
入れ直し・端末の移行・更新の後にも実行する。
終わったら、`/mcp` で MCP サーバーへ接続し直す。
`env` に `RULE_INJECT_PORT`・`RULE_INJECT_CONFIG` を記載したときは、Claude Code を起動し直す。

| 引数 | 内容 |
| --- | --- |
| `--clone` | サーバーを起動するローカルのクローンのパス |
| `--config` | 端末の設定のパス。既定と違うときは `~/.claude/settings.json` の `env` に `RULE_INJECT_CONFIG` を記載する |
| `--index` | 雛形の `global.indexes` に記載する索引のパス |
| `--service` | systemd のユーザーのユニットのサービス名（既定 `rule-inject`） |
| `--yes`・`--no` | 移し替えと旧い登録の削除の確認への回答 |

引数で指定しなかった値は質問する。
`claude mcp add` で `rule-inject` を登録済みの端末は、確認のうえ登録を削除する。

### 3. ルールの索引を書く

ルールの場所と、それを当てるパスの対応を YAML に書く。
書式は [索引の書式](../リファレンス/索引の書式.md)。

```yaml
rules:
  - rule: ./python.md
    paths:
      - "**/*.py"
    on: [write]
```

### 4. 索引を設定ファイルで指す

リポジトリの直下の `rules.yaml` は既定で読むので、スキル `setup` で確認だけを実行する。

```text
/rule-inject:setup
```

別の場所の索引を指定すると、端末の設定の `projects` に記載してチェックの結果を示す。

手で記載するときは、設定ファイル `${XDG_CONFIG_HOME:-~/.config}/rule-inject/settings.yaml` に索引のパスを記載する。
キーの一覧は、プラグインの直下の [settings.sample.yaml](https://github.com/shuhei1101/rule-inject/blob/develop/settings.sample.yaml)。

| 索引の用途 | 記載するキー |
| --- | --- |
| 全プロジェクトで使う | `global.indexes` |
| そのプロジェクトだけで使う | `projects` の要素の `indexes`（`match` でプロジェクトを指す） |

```yaml
global:
  indexes:
    - ~/rules/index.yaml
projects:
  - match: my-project
    indexes:
      - rules/project.yaml
```

どちらも複数の索引を並べられる。
`projects` の要素の書き方と当て方は [設定ファイル](../リファレンス/設定ファイル.md)。

設定ファイルを既定と違う場所に置くときだけ、`~/.claude/settings.json` の `env` にパスを置く。

```json
{
  "env": {
    "RULE_INJECT_CONFIG": "~/path/to/settings.yaml"
  }
}
```

プロジェクトの `.claude/settings.json` の `env` には置かない。
置いた後と変えた後は、Claude Code を起動し直す。
一覧は [環境変数](../リファレンス/環境変数.md)。

索引を既定の置き場所に置くときは、設定ファイルも環境変数も書かなくてよい。

| 索引の用途 | 既定の置き場所 |
| --- | --- |
| 全プロジェクトで使う | `${XDG_CONFIG_HOME:-~/.config}/rule-inject/rules.yaml` |
| そのプロジェクトだけで使う | プロジェクトの直下の `rules.yaml` |

### 5. ログと既読の記録の残し方を変える（任意）

既定のままでよければ飛ばす。
変えるときは、設定ファイルの `global` に記載する。

| 変えたいこと | キー | 既定値 |
| --- | --- | --- |
| ログを出すフォルダ | `global.log_dir` | `${XDG_STATE_HOME:-~/.local/state}/rule-inject/logs` |
| ログのファイルを残す日数 | `global.log_retention_days` | `3` |
| 既読の記録ファイルと既読の履歴ファイルを残す日数 | `global.record_retention_days` | `30` |

```yaml
global:
  log_dir: ~/logs/rule-inject
  log_retention_days: 7
```

設定ファイルを変えた内容は、次のフックの呼び出しから効く。

### 6. MCP サーバーを手で常駐させる（任意）

`global-setup` がサーバーを起動するので、手で管理するときだけ読む。
効いているルールの確認・ルールの検索・索引のチェックと編集をツールで行うときに使う。
フックはサーバーに依存しないため、サーバーを立てなくても案内は動く。
役割は [MCPサーバー](../はじめに/コアコンセプト/MCPサーバー.md)、ツールは [MCPツール](../リファレンス/MCPツール.md)。

ローカルのクローンで、サーバーの依存を入れて前面で起動する。

```bash
cd ~/repo/rule-inject
uv run --extra server python -m rule_inject.server
```

- 待ち受けるのは `127.0.0.1` の既定 `8783`。変えるときは環境変数 `RULE_INJECT_PORT` を、サーバーと `~/.claude/settings.json` の `env` の両方に置く
- 設定ファイルを既定と違う場所に置くときは、`RULE_INJECT_CONFIG` でフックと同じ設定ファイルを指す。`rule` の `!{名前}` を使う索引は、同じ名前の環境変数も起動する側に置く（[環境変数](../リファレンス/環境変数.md)）
- ポートが使われているときと、設定ファイルが読めないときは、待ち受けずに標準エラーへ理由を書き、0 以外の終了コードで終わる
- 止めるときは Ctrl+C か SIGTERM。SIGTERM の終了コードは 143

常駐させるときは、systemd のユーザーのユニットなどで起動する。
次は `~/.config/systemd/user/rule-inject.service` の例。

```ini
[Unit]
Description=rule-inject MCP server

[Service]
WorkingDirectory=%h/repo/rule-inject
ExecStart=%h/.local/bin/uv run --extra server python -m rule_inject.server
Restart=on-failure
SuccessExitStatus=143

[Install]
WantedBy=default.target
```

`SuccessExitStatus=143` は、SIGTERM で止めた終了を失敗として扱わないための指定。

```bash
systemctl --user daemon-reload
systemctl --user enable --now rule-inject.service
```

Claude Code は、プラグインの `.mcp.json` の `http://127.0.0.1:${RULE_INJECT_PORT:-8783}/mcp` へ接続する。
サーバーが止まっていても、Claude Code は接続の失敗を表示して起動し、フックの案内は動く。

セッションの開始時にサーバーが応答せず、ユニットが有効（`systemctl --user is-enabled`）なら、フックがユニットへ起動を依頼する。
サーバーが待ち受けを始めるまで数十秒かかり、そのセッションの最初の接続には間に合わないため、`/mcp` で `rule-inject` に接続し直すとツールを使用できる。
次に開くセッションは最初から接続できる。
起動するユニットは、端末の設定の `global.server_service`（既定 `rule-inject`）。`disable` したユニットは起動しない。

`RULE_INJECT_PORT` は、サーバーの起動時に 1 回だけ読む。
変えたときは、サーバーと Claude Code を起動し直す。

起動した後の再起動と更新は、サーバーのツールで行う（[MCPツール](../リファレンス/MCPツール.md)）。

| やりたいこと | ツール |
| --- | --- |
| コードを直した後に効かせる | `restart_server` |
| 新しいバージョンを入れる | `update_server`。クローンへ上流の commit を取り込み、`uv sync --extra server` の後に起動し直す。設定の移し替えが要ると返ったときは `/rule-inject:global-setup` を実行してから `restart_server` |
| 動いているバージョンと設定ファイルの読み取りを確かめる | `get_server_status` |

ツールでの再起動は環境変数を起動時のまま引き継ぐ。
`RULE_INJECT_PORT` や unit の `Environment=` を変えたときは、`systemctl --user restart rule-inject.service` で起動し直す。

## 確かめる

索引の `paths` に当たるファイルを Claude Code に書かせる。
1 回目は操作が止まり、ルールのパスが案内される。
案内されたルールを参照してからやり直すと、同じ操作が通る。
索引に `read_tool` を書いたルールは案内されたツールで、書いていないルールはパスを Read で参照する。
仕組みは [ルールの案内](../はじめに/コアコンセプト/ルールの案内.md)。

## 外すとき

設定ファイルの `global.indexes` を空の並び `[]` にし、使うプロジェクトごとに `projects` の要素の `indexes` も `[]` にすると、案内は出なくなる。
`indexes` を削除するだけでは、既定の置き場所に索引があればその索引で案内が出る。
