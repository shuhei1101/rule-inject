# 要件

## 要望

- `project-index.yaml` の `documents[].schema` を、knowledge の Schema の `source`・`path`・`ref` つきの参照へ切り替える。`ref` は `layout` の行と同じタグ（`design-schemas/v8.2.0`）にそろえる

  | 行 | 参照する Schema |
  | --- | --- |
  | 設計書の種類（`architecture`・`nonfunctional`・`scenario`・`interface`・`module`・`config`・`er`・`external_api`・`library`・`test_procedure`） | `schemas/design/{種類}.schema.yaml` |
  | `index` | `schemas/design/index.schema.yaml` |
  | 文書の一覧（`docs`・`src`・`hooks`・`tests`・`skills`・`root`） | `schemas/knowledge-files.schema.yaml` |

- `schemas/` から AI Monitor から配られた Schema のコピーと、設計書の変換 `schemas/conversions/` を削除する。変換は AI Monitor の `python -m ai_monitor.design_docs convert` が持つ（規約『ドキュメント管理』のトップ構造）
- 削除した Schema を指す箇所（`files.yml`・`files.yaml` の先頭の `yaml-language-server` の行、`pyproject.toml` の `schemas/conversions` の除外、`instructions`、フォルダ構成の設計書の `schemas` のエントリ）を、参照先の変更に合わせる
- 全ての設計書・目次・文書の一覧が、`project-index.yaml` の指す Schema の検査に合格する。origin/develop（[7e516f3](https://github.com/shuhei1101/rule-inject/commit/7e516f3)）での不合格は次のとおり

  | 種類 | 不合格 / 件数 | 内容 |
  | --- | --- | --- |
  | scenario | 25 / 25 | `issue` キーが Schema に無い |
  | module | 13 / 62 | `directory` キーが無い（11）、`data_models` の `properties[].name` が文字列でない（2） |
  | er | 2 / 2 | `tables[].source`（保存するデータの設計書のキー）が必須 |
  | nonfunctional・config | 2 / 2 | `introduced` キーが無い |

`未確定`: 用語集（`glossary`）の行の Schema（決める工程: ドキュメント修正）

knowledge の `schemas/terms.schema.yaml` は knowledge 自身の用語集の Schema で、`kind: terms` と knowledge の共通メタデータを求め、このリポジトリの `docs/glossary/` とスキーマが違う。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `glossary.schema.yaml` と、それが指す `common.schema.yaml` だけを knowledge から参照しない Schema として `schemas/` に残す | フォルダ構成の設計書の「knowledge から参照しないスキーマは `schemas/`」のとおりで、このリポジトリで完結する | 用語集の Schema だけコピーのまま残る |
| B | knowledge に設計書の用語集の Schema を追加する Issue を起票し、入るまで A で配置する | 全ての行が knowledge の参照になる | 他のリポジトリの作業を待つ |

推奨: A

knowledge の設計書の Schema に用語集の種類が無く、AI Monitor の配信元の設定も用語集の行を持たないため、今は参照先が無い。

`未確定`: `er` の `tables[].source` の記載（決める工程: ドキュメント修正）

`source` は保存するデータの設計書（`data`）のキーを指すが、このリポジトリに `data` の設計書は無い。

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `project-index.yaml` に `data` の行を追加し、ER の各テーブルが保存するデータの設計書を作って `source` で指す | Schema のとおりに ER とデータの対応を辿れる | 設計書の種類が 1 つ増える |
| B | `er` の行だけ今のコピーを残す | 作業が増えない | Schema のコピーを持たない決定に反する |

推奨: A

`source` は Schema の必須の項目で、B はこの Issue の要望（コピーの削除）を満たさない。

`未確定`: `scenario` の `issue` と `module` の `directory` の情報の扱い（決める工程: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | キーを削除する。シナリオを入れた Issue は git の履歴と PR ドキュメントが、モジュールのフォルダはフォルダ構成の設計書が持つ | 同じ情報を 2 か所に持たない | シナリオから Issue へのリンクが設計書から消える |
| B | Schema に残るキー（`refs`・`description` など）へ移す | 設計書の中に情報が残る | Schema がキーを削除した意図と合わない |

推奨: A

knowledge の Schema は、キーを設ける条件を見直してこれらのキーを削除しており（[shuhei1101/knowledge#266](https://github.com/shuhei1101/knowledge/pull/266)）、移し先のキーを作るとその判断と食い違う。
