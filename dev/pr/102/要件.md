# 要件

## 要望

索引のエントリごとに、ルールを参照する MCP のツールと引数を記載でき、案内文にそのツールと引数を載せる。

- 記載したエントリのルールは、案内文で「次のツールで参照する。使えないときは下の場所を Read で参照する」の順に案内する。ツールと引数に加えて、ルールの場所も Read の代わりとして載せる
- 止める案内（ルール案内の `permissionDecisionReason`）・止めない案内（ルール案内の `additionalContext`）・検索結果の案内（検索結果の案内の `additionalContext`）の全てに載せる
- 記載の無いエントリのルールは、今の Read で参照する案内のまま出す
- 案内したツールと引数で参照した後に同じ操作をやり直すと、止められずに通る（そのルールが既読になる）。`sections` を指定して一部だけを返す呼び出しも既読にする
- 新しいキーは任意で、記載の無い既存の索引はそのまま読める
- MCP サーバーの『エントリの書き込み』で新しいキーを書け、『ルールの一覧』の応答に新しいキーが載り、『索引のチェック』が新しいキーの値を JSON Schema で確かめる
- 監視対象の各プロジェクトへ、索引のエントリに新しいキーを記載する反映作業を知らせる。dev-docs の配信元の文書を指すエントリは、MCP のツールで参照する案内にする（[Issue #100 の追加の要望](https://github.com/shuhei1101/rule-inject/issues/100#issuecomment-6604618168)）

確定（インターフェース定義設計）: 案 A。キーは `read_tool`（`tool`・`args`）で、`args` は呼び出しの引数の最上位に書いた全てのキーがあり値が等しければ一致とする（呼び出しの余分なキーは問わない）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | エントリに新しいキーを追加し、案内に載せるツールの完全名と引数の値をそのまま記載する | 引数の値を具体的に書け、案内文にそのまま載せられる | エントリのキーが 1 つ増える |
| B | 既存の `read_by` の `tools`・`args` から案内文を組み立てる | キーが増えない | `read_by` は glob か正規表現のパターンで、具体的な引数の値を組み立てられない |

推奨: A

`read_by` は呼び出しに当てるパターンで、`re:^...` のような値を案内に載せても読み手が呼べない。
案内の呼び出しは、ツール名と引数が新しいキーの記載と一致すれば、結果の範囲（`scope`）と `read_by` によらず既読にする。

| 項目 | 理由 | 対応予定 |

| knowledge の索引のエントリへの新しいキーの記載 | knowledge のリポジトリの索引の変更で、この機能を使う側 | [shuhei1101/knowledge#158](https://github.com/shuhei1101/knowledge/issues/158) |

| MCP サーバーの『ルールの検索』の応答への、エントリに記載したツールと引数の追加 | 判断が分かれる。`list_rules` の応答にキーが載れば索引の作成者は記載を確かめられ、『ルールの検索』は当たるルールと止めるかを返す役のため、今の判断はスコープ外とする。インターフェース定義設計のレビューで確定する | 予定なし |
