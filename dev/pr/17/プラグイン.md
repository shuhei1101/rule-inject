## 変更方針

| 対象 | 方針 | 補足 |
| --- | --- | --- |
| 索引の既定の置き場所 | `RULE_INJECT_INDEXES_USER` が無いときは `${XDG_CONFIG_HOME:-~/.config}/rule-inject/rules.yaml`、`RULE_INJECT_INDEXES_PROJECT` が無いときは `${CLAUDE_PROJECT_DIR}/rules.yaml` を読む。既定のファイルが無いとき・`CLAUDE_PROJECT_DIR` が無いときは、理由を載せずに読まない | 環境変数を空の文字列にしたときは、既定の置き場所も読まない（下の論点の A。インターフェース定義設計で決めた） |
| 変数参照の展開 | `!{名前}`（`[A-Za-z_][A-Za-z0-9_]*`）を環境変数の値に置き換える。空の値は空文字、未設定の名前は残す。本文の展開と索引の `rule` の展開は同じ関数を使う | フックは Claude Code から、MCP サーバーは起動時に、同じ `settings.json` の `env` を受け取る |
| 本文の展開 | `read_rules` は読んだ本文を展開し、未設定の名前があれば本文の先頭に注釈を 1 行足してから、応答の上限に収める | 既読の記録は今のとおり場所で書く |
| 索引の `rule` の展開 | 索引を読むときに `rule` を展開してから場所を解く。未設定の名前が残ったエントリは読み飛ばし、索引が読めないときと同じくログとコンテキストへ理由を載せる | 理由を載せるのはフック（`PreToolUse`・検索結果の案内）。MCP サーバーは読み飛ばすだけ |
| 案内済みの記録 | 止めない案内に載せた場所を `{RULE_INJECT_STATE_DIR}/{session_id}.guided.txt` に 1 行ずつ追記し、次からはその場所を止めない案内に載せない | 止める案内は今のとおり、読むまで毎回止める。追記の形は既読の記録と同じ（`O_APPEND` で 1 回に書く） |
| 検索結果の案内 | `PostToolUse` で、Grep・Glob の結果のファイル名と、`grep` `rg` `find` `ls` の Bash の出力から、実在するファイルの絶対パスを拾い、読む操作として当たる未読で未案内のルールを止めずに案内する | 読むかは任意と伝える文面にする |
| 案内済みの記録の破棄・掃除 | 圧縮の前に `{session_id}.guided.txt` も消し、セッションの開始時の掃除でも保持期間を過ぎた `{session_id}.guided.txt` を消す | 保持期間は既読の記録と同じ `RULE_INJECT_RECORD_RETENTION_DAYS` |
| 実行時間・案内文の長さ | 検索結果の案内も、非機能要件「フックの実行時間」と「フックの案内文の長さ」に収める | 照合するパスは結果の先頭 100 件まで（非機能要件「検索結果から照合するパスの数」。索引 231 件での 1 パスあたりの照合の実測から導いた）。Grep・Glob・Bash の `tool_response` の形は、2026-10-11 に Claude Code 2.1.296 の `PostToolUse` で確かめた |
| 対応テストファイル | 新しく作るテストファイルは、書くツールが実在しないファイルを受け付けないため、テストの作成までの間は設計書から外している | 単体テスト作成でモジュール構成『共通』の `test_files` に `tests/unit/rule_inject/shared/test_variables.py`、『フック』に `tests/unit/rule_inject/hooks/test_search_guide.py`、結合テスト作成でインターフェース定義「検索結果の案内」の `test_file` に `tests/integration/plugin/test_search_guide.py`、E2E テスト作成で単一ユースケース「検索の結果に出たファイルのルールの案内を受ける」の `test_file` に `tests/e2e/単一ユースケース/test_receive_guidance_for_search_results.py` を足す |
| `hooks.json` | `PostToolUse` に `Grep\|Glob\|Bash` の検索結果の案内の行を足す（timeout は既存の行と同じ 1 秒） | 既読の記録の行（`Read\|Bash`）は変えない |

### 論点: 索引の環境変数を空の文字列にしたときの扱い

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 環境変数が無いときだけ既定の置き場所を読み、空の文字列にしたときは何も読まない | 既定の索引を止める手段が残る | 「無い」と「空」で振る舞いが分かれる |
| B | 空の文字列も無いときと同じく既定の置き場所を読む | 振る舞いが 1 つで分かりやすい | 既定の置き場所にファイルがあると、読ませない手段が無い |

推奨: A

既定の置き場所に別の用途の `rules.yaml` があるプロジェクトでも、環境変数を空にすれば読ませずに済むため。
